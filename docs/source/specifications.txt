1. INTRODUCTION
1.1 Purpose
This Software Requirements Specification (SRS) defines the functional and non-functional requirements of GEONARA MVP 1.0.
It establishes what the software must do, how users interact with its main modules, and what technical and operational conditions must be satisfied.
This document serves as a reference for:
Software developers.
UI/UX designers.
Backend engineers.
Database engineers.
Quality assurance engineers.
Project owner.
1.2 Project Overview
GEONARA is a specialized digital platform dedicated to geology, Earth sciences, scientific research, and professional interaction.
The platform aims to provide a centralized environment where students, researchers, academics, and professionals can access geological knowledge, discover scientific publications, use AI-assisted scientific tools, and communicate with other members.
GEONARA is designed as a specialized scientific platform rather than a general-purpose social network.
1.3 MVP Scope
The first release includes five principal modules:
GEONARA Dictionary.
GEONARA Research.
GEONARA AI.
User Profiles.
Direct Messaging.
Features not explicitly included in these five modules are outside the confirmed MVP scope unless approved by the project owner.

2. PROJECT SCOPE
2.1 Primary Objectives
GEONARA MVP 1.0 must:
Provide access to geological terminology and definitions.
Allow users to discover scientific publications.
Provide an AI assistant specialized in geological subjects.
Allow users to create and manage scientific profiles.
Allow direct communication between users.
Support three initial interface languages.
Provide a consistent mobile experience.

University students studying:
Geology.
Petroleum geology.

Earth science industries.

3. SYSTEM USERS AND ACCESS CONTROL
3.1 Guest User
A guest is an individual who accesses the application without creating an account.
The availability of public content to guests must be determined by the project owner.
Proposed behavior:
Access public introductory information.
View approved public dictionary content.
Access registration and login screens.
Access to AI, messaging, and personal profile functions requires authentication unless otherwise approved.
3.2 Registered User
A registered user has an authenticated GEONARA account.
The registered user should be able to:
Manage their profile.
Access GEONARA AI.
Explore GEONARA Research.
Use GEONARA Dictionary.
Send and receive direct messages.
Manage account settings.
3.3 Administrator
An administrator is responsible for managing platform content and operational activities.
Potential responsibilities:
Manage dictionary entries.
Review and publish scientific terminology.
Manage reported content.
Manage user accounts according to approved policies.
Monitor platform activity.
Manage approved scientific resources.
The exact administrative interface and permission hierarchy require owner approval.
3.4 Role-Based Access Control
The system must enforce permissions on the backend.
Hiding a button or screen in the mobile application is not sufficient to protect a restricted operation.
Every protected API operation must validate the authenticated user's permissions.

4. FUNCTIONAL REQUIREMENTS
4.1 USER ACCOUNT AND AUTHENTICATION
4.1.1 Account Registration
Requirement ID: AUTH-001
The system should allow a new user to create a GEONARA account.
Proposed registration fields:
Full name.
Email address.
Password.
Preferred interface language.
Additional profile information should be collected after registration rather than making the initial registration unnecessarily complicated.
Acceptance Criteria:
The user can submit valid registration information.
The system validates required fields.
Duplicate email addresses are rejected.
Passwords are securely stored using an appropriate password-hashing mechanism.
The system returns a clear registration result.
Email verification is proposed but requires confirmation before implementation.
4.1.2 User Login
Requirement ID: AUTH-002
The system must allow registered users to authenticate using their approved credentials.
Acceptance Criteria:
Valid credentials grant access.
Invalid credentials are rejected.
Authentication errors are displayed clearly.
Sensitive authentication information is not exposed.
4.1.3 Logout
Requirement ID: AUTH-003
Users must be able to terminate their authenticated session.
4.1.4 Password Recovery
Requirement ID: AUTH-004
The system should provide an approved password recovery process.
The process must not reveal whether an arbitrary email address belongs to an existing account.
4.1.5 Account Settings
Requirement ID: AUTH-005
Users should be able to access their account settings.
The following functions require final UI/UX and policy definition:
Change password.
Change preferred language.
Review account information.
Request account deletion.

4.2 USER PROFILES
4.2.1 Profile Creation
Requirement ID: PROF-001
Every registered user must have a basic GEONARA profile.
The profile may include:
Full name.
Profile image.
Professional or academic title.
Biography.
Country.
Institution or organization.
Academic discipline.
Scientific interests.
Skills.
Languages.
Research interests.
Not all fields must be mandatory.
4.2.2 Profile Editing
Requirement ID: PROF-002
Users must be able to update their own profile information.
Users must not be able to modify another user's private profile data.
4.2.3 Public Profile Viewing
Requirement ID: PROF-003
The system should allow users to view other members' profiles according to their privacy settings.
The profile should display only information that the profile owner has permitted to be visible.
4.2.4 Profile Discovery
Requirement ID: PROF-004
The system should support discovering other users.
Potential search criteria:
Name.
Scientific discipline.
Academic institution.
Professional specialization.
Country.
The exact search filters and ranking behavior require approval.
4.2.5 Profile Privacy
Requirement ID: PROF-005
The system must respect user privacy preferences.
Private information must not become publicly accessible through API responses.

Users can enter a search query.
Relevant terms are returned.
Empty search results are handled clearly.
Search input is validated.
Results are displayed in a readable format.

Each dictionary entry should support the following information where available:

Scientific definition.
Language.
Scientific category.
Synonyms.
Related terms.

Publication or review status.
4.3.5 Multilingual Terminology
Requirement ID: DICT-003
The dictionary should support English, French, and Arabic terminology.
A scientific term may have equivalent names in multiple languages.
The system must preserve the relationship between equivalent terminology entries.
4.3.6 Related Terms
Requirement ID: DICT-004
Users should be able to discover related geological concepts from a term details page.

Requirement ID: DICT-005
Authorized administrators should be able to:
Create dictionary entries.
Edit entries.
Assign scientific categories.
Review entries.
Publish approved entries.
Archive entries.
The publication workflow must prevent unauthorized users from modifying official dictionary content.
4.3.8 Content Quality
Dictionary definitions should be scientifically reviewed before being marked as approved content.
Unreviewed content must be distinguishable from approved content internally.

4.4.1 Module Purpose

Usage limits.

Commercial usage restrictions.
Service availability.

Requirement ID: RES-005
The system must preserve the original publication identity and source attribution.
It must not present metadata from an external provider as if GEONARA had independently published the original research.

A saved-publication or personal-library feature is not yet confirmed for MVP 1.0.
Its inclusion requires owner approval.

Open an existing conversation.

Distinguish retrieved evidence from model-generated explanations.

It can help improve factual grounding and provide traceable sources.
RAG does not guarantee that every generated answer will be correct.
9.2 Proposed Processing Pipeline
Scientific document ingestion.
Text extraction.
Document cleaning.
Document segmentation (chunking).
Metadata association.
Embedding generation.
Vector indexing.
Semantic retrieval.
Optional reranking.

AI response generation.

Chunking should preserve:

Paragraph context.
Section relationships.
Tables and figure references when extractable.
Relevant metadata.
Chunk size and overlap must be determined through testing rather than arbitrary fixed values.

Embedding models may be used to represent scientific text as numerical vectors.

Multilingual performance.
Scientific terminology handling.
Retrieval accuracy.
Vector dimensions.
Processing cost.
Commercial usage permissions.

Indexing requirements.
Infrastructure cost.
Integration complexity.
A separate vector database should not be introduced unless justified by measurable requirements.

class ResearchProvider:

Exact provider record identity.
Normalized publication title combined with author information and publication year.

8.3 Record Merging

Conflicting values must not be silently overwritten.
The source of each important field should remain traceable.
Different versions or editions must not automatically be merged.
8.4 Preprints and Published Articles
A preprint and its subsequently published journal article may represent related but distinct records.

14. DATA VALIDATION AND CONSTRAINTS
The developer must implement appropriate database-level validation.
Examples:
14.1 User Accounts
Email must be unique after normalization.
Password hash must never be plaintext.
Account status must belong to the approved set.
Role assignments must reference existing users and roles.
14.2 Profiles
Each user must have at most one profile.
Display name must not be empty.
Country code must follow the selected country-code standard.
Profile fields must respect approved length limits.
14.3 Dictionary
Each term must have a unique slug.
A term cannot be related to itself.
A term cannot have duplicate translations for the same language.
Only published terms may appear in ordinary dictionary search.
Definitions must not be empty.
14.4 Research
External record identifiers must be unique within their provider.
DOI values must be normalized.
Author order must be positive.
Missing metadata must remain NULL rather than being fabricated.
14.5 AI
Each conversation must belong to an existing user.
Each AI message must belong to an existing conversation.
Message roles must belong to the approved set.
Source references must be associated with valid AI responses.
14.6 Messaging
A direct conversation must contain exactly two distinct participants.
A sender must belong to the conversation.
A user cannot block themselves.
A user cannot report themselves.
Duplicate block relationships must be prevented.
Some rules, particularly the exact participant count for a direct conversation, require transactional backend enforcement in addition to database constraints.
15. DATABASE SECURITY
The database must follow security best practices.
Requirements:
The application must connect using a restricted database account.

2. BACKEND ARCHITECTURE

GEONARA MVP 1.0 will use a Modular Monolith Architecture.
This means that the backend will operate as one deployable application, but its internal code will be divided into independent functional modules.
The architecture must avoid unnecessary microservices during the initial development phase.
Reasons for this choice
Lower initial infrastructure complexity.
Easier development and debugging.
Centralized authentication and authorization.
Simplified database transactions.
Easier deployment and maintenance.
Clear separation between application modules.
Possibility of extracting independent services in the future.
2.2 Main Backend Modules
The backend must contain the following logical modules:
Authentication Module.
User and Profile Module.
Dictionary Module.
Research Module.
AI Module.
Messaging Module.
Notification Module.
Administration and Moderation Module.
Each module must contain its own business logic and data-access responsibilities.
One module must not directly manipulate another module's internal data through uncontrolled database operations.
Cross-module operations should use clearly defined service interfaces.

6.2 Access Token

Identify the authenticated user.

2. PRODUCT OVERVIEW
2.1 Product Vision
GEONARA is a specialized scientific and professional platform dedicated to geology and Earth sciences.
It aims to provide a unified digital environment where students, researchers, academics, and geoscience professionals can:
Access reliable geological terminology and definitions.
Discover scientific publications and research.
Interact with an AI assistant specialized in geology and Earth sciences.
Create professional scientific profiles.
Communicate directly with other platform members.
GEONARA is not intended to be a general-purpose social network. Its primary focus is scientific knowledge, research, professional identity, and specialized communication.
2.2 MVP Scope

GEONARA Dictionary
GEONARA Research
GEONARA AI
User Profiles
Direct Messaging
Authentication, account management, notifications, and administrative functions are supporting system capabilities, not additional main product modules.
2.3 Target Users

Geology students.
Master's and doctoral students.
Academic researchers.
University professors.
Geological engineers.
Geoscientists and Earth science professionals.
Other users with a legitimate scientific interest in geology.
3. USER ROLES AND PERMISSIONS
3.1 Visitor
A visitor is a person who has not authenticated.
Proposed permissions:
View public landing and introductory screens.
View basic information about GEONARA.
Access account registration and login screens.
Access to scientific content without authentication remains a decision pending owner approval.
3.2 Registered User
A registered user is an authenticated member of GEONARA.
Permissions:
Access available Dictionary content.
Search and explore scientific publications.
Use GEONARA AI subject to applicable usage limits.
Create and manage a personal profile.
Search for other users.
Send and receive direct messages, subject to messaging permissions.
Manage account settings and privacy preferences.
3.3 Administrator
An administrator manages the platform's content and operational integrity.
Proposed permissions:
Manage dictionary categories and terms.
Review and publish submitted dictionary suggestions.
Manage reported content and user reports.
Manage user accounts where authorized.
Review platform-level operational information.
Manage selected system settings.
Administrator access must be protected by role-based authorization.
3.4 Role-Based Access Control
The backend must enforce permissions independently of the mobile interface.
Hiding a button in the application is not sufficient security. Every protected operation must be validated by the backend.

5. MODULE 01 — GEONARA DICTIONARY
5.1 Module Objective
GEONARA Dictionary is a specialized geological terminology reference.
It must help users understand scientific concepts, terminology, classifications, and definitions used in geology and related Earth sciences.
The module must prioritize scientific accuracy, clarity, consistency, and multilingual terminology.
5.2 Dictionary Main Screen
The screen must provide:
Module title.
Search field.
Geological categories.
Alphabetical browsing.
Recently added terms, if available.
Featured or recommended terms, if configured.
5.3 Geological Categories
The system must support hierarchical or structured categories.
Initial proposed categories:
General Geology.
Mineralogy.
Petrology.
Sedimentology.

Structural Geology.
Tectonics.

Georesources and Energy Resources.

The final category structure must be reviewed before database implementation.
5.4 Dictionary Search
The user must be able to search for a geological term.
Search requirements:
Search by term name.
Support partial text matching.
Support the available language variants.
Display relevant matching results.
Provide a clear empty-results state.
Handle spelling variations where technically feasible.

A user searches for "Diagenesis".
The system returns matching dictionary entries and allows the user to open the relevant term.

Scientific definition.
Explanation.

Translation into supported languages.
Related terms.
Scientific references.

Assign categories.
Add translations.
Add scientific references.
Publish or unpublish entries.
A proposed content status system:

Under Review.
Published.
Archived.

A new geological term.

A translation correction.
A scientific reference.

GEONARA Research is a scientific discovery module designed to help users find academic publications and research relevant to geology and Earth sciences.

7. MODULE 03 — GEONARA AI
7.1 Module Objective
GEONARA AI is a specialized artificial intelligence assistant dedicated to geology and Earth sciences.
Its purpose is to assist users with scientific understanding, terminology, geological interpretation, academic research, and technical questions.
It must not be presented as an infallible scientific authority.
7.2 AI Main Interface
The interface must provide:
Conversation area.
Message input field.
Send action.
New conversation action.
Conversation history.
Loading or processing indicator.
Error state.
Source references when available.
7.3 User Questions
Users must be able to submit questions in supported languages.
Examples:
Explain the depositional environments of a carbonate platform.
What is the difference between porosity and permeability?
Explain the main stages of diagenesis.
Describe the geological evolution of the Saharan Platform.
The AI service should recognize geological terminology and respond using scientifically appropriate language.
7.4 AI Response Requirements
Responses should:
Address the user's question directly.
Use accurate geological terminology.
Structure complex explanations.
Distinguish established facts from interpretations.
Identify uncertainty when relevant.
Avoid fabricating scientific references.
Provide references or source links when supported by the system.
The AI must not claim that a statement is scientifically verified when it has no reliable basis for that claim.
7.5 Language Behavior
The assistant should respond in the language used by the user unless the user requests another language.
It should support scientific terminology in English, French, and Arabic.
Where useful, it may provide the scientific term in another language.
Example:
"التحجر — Lithification — Lithification"
7.6 Conversation Management
Users should be able to:
Start a new conversation.
Send messages.
View previous conversations.
Open an existing conversation.
Delete a conversation, subject to the final retention policy.
The application must associate each conversation with its authorized owner.
A user must never be able to access another user's private AI conversations.
7.7 Context Management
The AI service should use the relevant conversation context to maintain continuity.
However:
Context must be scoped to the correct conversation.
Private conversations must remain isolated.
The system must handle context limitations.
The assistant must not pretend to remember information that is not available.
7.8 Scientific Sources and Retrieval
A retrieval-based architecture (RAG) is proposed for grounding responses in selected scientific materials.
Potential capabilities:
Retrieve relevant scientific documents.
Extract relevant passages.
Generate an answer based on retrieved information.
Attach source references.
Distinguish retrieved evidence from general model knowledge.
The source corpus, licensing model, indexing strategy, and AI provider must be specified in a separate technical document.
7.9 AI Usage Controls
The system should support configurable limits such as:
Maximum request length.
Maximum response length.
Request frequency.
Usage quotas.
Protection against automated abuse.
The actual quotas and any cost-related policies require owner approval.
7.10 AI Failure Handling
The application must handle:
AI provider unavailable.
Request timeout.
Invalid response.
Usage limit reached.
Network interruption.
Unsupported request.
The application must not silently discard user messages.
7.11 AI Acceptance Criteria
The module is accepted when:
Users can send questions.
Responses appear correctly.
Conversation history is maintained.
Users can create new conversations.
Conversations remain private.
Errors are communicated clearly.
Usage limits are enforced by the backend.
References are displayed only when valid source data exists.

6. API DESIGN STANDARDS
6.1 Base URL
All version 1 API endpoints must follow:
/api/v1/
Example:
/api/v1/profiles/me
6.2 HTTP Methods
Method
Purpose
GET
Retrieve information
POST
Create a resource or execute an action
PUT
Replace a resource representation
PATCH
Partially update a resource
DELETE
Delete or request deletion of a resource
The backend must use HTTP methods consistently.
6.3 Data Format
Requests and responses should use JSON unless the endpoint requires another content type, such as file upload.
Example:
{
  "status": "success",
  "data": {
    "id": "resource-id",
    "name": "Example"
  }
}
This is an illustrative response structure. Exact response schemas must be defined per endpoint.
6.4 Authentication Header
Protected endpoints must require valid authentication.
Proposed header:
Authorization: Bearer <access_token>
The actual token format, expiration, refresh mechanism, and storage strategy must be defined in the security implementation.
6.5 Pagination
List endpoints must support pagination where appropriate.
Proposed query parameters:
?page=1&page_size=20
Rules:
Page numbers must be positive.
Page size must have a configurable maximum.
The backend must not return unlimited records.
Ordering must be deterministic.
Pagination metadata should be included where useful.
6.6 Filtering and Sorting
Search and listing endpoints may support documented filters and sorting parameters.
Only explicitly supported parameters may be accepted.
The backend must reject or safely ignore invalid values according to the endpoint contract.
6.7 API Documentation
FastAPI should generate OpenAPI documentation.
Development documentation should be available through:
/docs
/redoc
Production exposure of interactive documentation must follow the deployment security policy.

12.6 AI Processing Strategy
Two processing approaches are possible.
Synchronous Processing
The API waits for the AI provider and returns the completed response.
Advantages:
Simpler implementation.
Easier initial testing.
Limitations:
Long requests may exceed HTTP timeouts.
Less suitable for long-running processing.
Asynchronous Processing
The API accepts the request and returns a processing identifier or message state.
The client retrieves the result through an approved polling or event mechanism.
Advantages:
Better support for long-running requests.
More flexible processing.
Better control of background tasks.
MVP recommendation: Start with synchronous requests if the selected AI provider reliably meets response-time requirements. Introduce asynchronous processing when measured performance or provider behavior justifies it.
12.7 AI Provider Abstraction
The backend must not tightly couple business logic to a single AI provider.
Proposed structure:
ai/
│
├── providers/
│   ├── base_ai_provider.py
│   └── selected_ai_provider.py
│
├── services/
│   ├── ai_service.py
│   ├── conversation_service.py
│   ├── prompt_service.py
│   └── citation_service.py
│
└── repositories/

12.8 AI Scientific Grounding
A Retrieval-Augmented Generation (RAG) architecture is proposed for scientific grounding.
Potential workflow:
Receive the user question.
Identify relevant scientific terminology or topics.
Search the approved knowledge corpus.
Retrieve relevant document passages.
Provide selected passages to the AI model.
Generate the response.
Attach valid source references.
Store the result.
The knowledge corpus must use sources that GEONARA is permitted to process.
RAG must not be presented as a guarantee of scientific correctness.
